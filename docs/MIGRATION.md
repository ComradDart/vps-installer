# Миграция существующего сервера

Автоматического импорта старой БД и перевода старого AWG/MTProxyL маршрута нет.
Старые state-файлы не исполняются. Новый корень `/opt/vps-installer` отделён от
`/opt/3x-ui`, `/opt/nginx-panel`, `/opt/mtproxyl`, `/opt/telemt`, `/etc/amnezia`.

1. Snapshot у провайдера + проверить вход через serial/VNC console.
2. Сохранить старый конфиг, Docker compose/inspect, правила UFW/iptables и ключи
   вне VPS. Backup новой программы захватит обнаруженные legacy-каталоги до изменений.
3. Снять инвентаризацию `ss -lntup`, всех Docker PortBindings, systemd services,
   SSH config, активных AWG-интерфейсов и маршрутов. Отдельно учесть shared 80/443.
4. Предпочтительно развернуть новую конфигурацию на чистой тестовой VPS и перенести DNS.
   Старый сервер остаётся доступным для отката.
5. На том же сервере сначала согласовать maintenance window. Установщик при конфликте
   80/443/2053/8443 остановится и не остановит чужой сервис. Только администратор после
   backup явно останавливает нужный старый compose/service. Не удаляйте его data volumes.
6. Старые AWG UDP rules и interfaces остаются до отдельного решения администратора.
   `--check` может сообщить о лишних listener/rules; это ожидаемая ручная часть миграции.
   Новый установщик не использует и не перезагружает старые AWG-конфигурации.
7. Старую БД можно переносить только при проверенной совместимости с актуальным latest
   и отдельном тесте. Не копируйте активную SQLite без online snapshot/WAL. Отдельно
   привести web port/base path/listen/security к контракту новой панели. Автоопределение
   чужих настроек вместо проверки здесь не используется.
8. Перенос сайта — явное копирование в `.../site` перед повторным запуском. Готовый
   существующий сайт обычный запуск не заменит. Новые generated compose/nginx конфиги
   принадлежат установщику; свои дополнительные изменения учитывайте отдельно.

Rollback приложения: сохранённый snapshot VPS или предыдущий stack backup с совместимым
образом. Rollback SSH: отдельный drop-in rollback; system.tar.gz внутри backup предназначен
для ручного восстановления из консоли, а не бесконтрольного tar extract в `/`.
